# Stage-scoped preflight and repair

When `--stage` is present, record the requested stage, operation, completed prior stages, and direct dependencies. Under `--inspect`, perform read-only checks and return before any claim, comment, edit, install, branch, commit, push, browser, deployment, or project-doc generation. Under `--repair`, repair only the named stage's missing prerequisite, verify it through its native read-only operation, and return control to the original authorized caller. The caller retries its operation once; setup never inherits issue, PR, or deployment mutation authority. A second failure or an operation absent from an older descriptor returns a specific blocker or documented same-semantics fallback; it never loops into full setup.

Tracker-only Jira work accepts configured or explicitly supplied site, project, and transport. It checks only the required Jira operation set and does not probe GitHub, AWS, browsers, application dependencies, or repository state. For `acli`, reuse only a compatible authenticated installation whose parsed site and local account binding match the authorized target. A prerequisite-only repair runs only `references/acli-setup.md`, verifies auth, target, and the required native command surface, then returns. For MCP, bind the selected provider tools, prove every required suffix, and execute a visible-project read or safe bounded JQL query proving scoped project access. Tool visibility or a shell message is not a probe; an existing issue key is not required for create/intake. Never install or fall back to `acli` in MCP mode.

Return a usable read-only selected binding even when project config or the installed descriptor is absent: provider, transport, site, project, the shipped descriptor path/content selected for this call, verified operation set, and scoped-access result. This return is ephemeral and writes no config or descriptor. A tracker stage must defer default branch resolution and every companion code-host operation.

Other stages check only their direct dependencies: repository (code host and target repository), implementation (repository plus project validation commands), QA (the selected local/PR/deployed evidence path), or publication (the exact provider target and prerequisites already authorized by the caller). Missing later-stage capability never blocks an earlier stage.
