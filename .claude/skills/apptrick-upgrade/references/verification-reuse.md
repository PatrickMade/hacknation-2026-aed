# Adopt verification reuse without discarding project extensions

Run this check independently of repository-root upgrade-note availability. This
is a source-policy upgrade, not authority to install packages, weaken required
product/live QA, change accounts, or deploy anything.

1. Confirm the project and its owning installer. For a pinned complete Harness,
   the authorized installation owner updates from a clean checkout of an accepted
   source revision using the existing `apptrick-set-up` package-install procedure.
   The source must be Git-tracked and clean; both client skill roots and the
   managed lock update together. Do not hand-edit installed managed copies. Keep
   local-only skills/extensions and unrelated client configuration. A modified
   managed file is a conflict to reconcile with its local owner, not permission
   to force-overwrite it. Native CLI installs retain their original scope and
   selected skills rather than changing to another installation mode.
2. Inspect the effective AGENTS/CLAUDE instruction owner, SDLC, repo-local skill
   extensions, wrappers and active run continuation instructions. Preserve import
   direction and pointer-only bridges. Search for duplicate full validation gates,
   module/test-file-count reruns, forced repeated review/history, resource byte
   quotas, RAM/CPU/disk floors, reservations, peer ACKs and episode clocks.
   Distinguish actual provider/protocol/user limits and real shared-resource
   ownership from invented admission. Never delete parsed chaining fields, stable
   run identity, authentication roles or product/live QA and release approvals.
3. Compare each match to Verification reuse, Independent review and Execution
   resources in this skill's own `references/rules.md`. Change the owning rule
   and any executable predicate with regression coverage; appending a prose
   exception while a wrapper still rejects work is not adoption. Keep useful
   local additions. List exact differences; apply already authorized scope
   without asking again. `--dry-run` writes nothing; `--yes` alone permits only
   non-conflicting additive changes. Uncovered conflicts retain the normal
   upgrade approval boundary.
4. Retain existing task/spec/run/PR identity, evidence and history. For ordinary
   local verification, inspect command, exit status, relevant output and current
   inputs/environment (including untracked files). Reuse unchanged valid results
   and accepted review scope; rerun missing or invalidated checks. Preserve
   explicitly fresh project/live/release gates and current required green CI.
5. Run the source-backed package `--check` from the existing installer procedure
   and the affected project verifier. Package integrity does not attest local
   extensions or model obedience. Verify the effective rules and owning script
   predicates, confirm a second inspection proposes no duplicate additions, and
   report exact files/revision, checks, retained extensions and unresolved gaps.

The canonical source owner delivers this procedure and source revision. Each
installation owner coordinates adoption separately; source acceptance does not
claim deployment to installed adaptations.
